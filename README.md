## Questão 1
Para o módulo ERP descrito, criaria microserviços para lidar com a entrada de pedidos, com a contagem de estoque e com o registro de movimentações.<br>
Assumindo que o módulo de clientes se refere à plataforma por são agregados os pedidos de clientes, e que o módulo financeiro refere-se à plataforma de onde são gerados relatórios financeiros, usaria uma API gateway para direcionar as requisições e realizar controle de permissões com base na sessão do usuário (ex. impedir que uma requisição vinda do módulo de clientes faça pedidos de relatórios financeiros).<p>
Idealmente, um domínio diferente para ambos seria mais apropriado, na minha opinião. No entanto, dado as configurações corretas do gateway, esta estrutura poderia ser usada de forma segura e utilizar um mesmo domínio.<p>
Para comunicação entre módulos referindo aos pedidos de clientes, utilizaria filas de mensagens assíncronas, como no diagrama, para disparar as chamadas necessárias para verificar se o pedido é válido (se o item pedido está em estoque, e atualizar o mesmo caso o pedido prossiga). As filas serão configuradas para que sejam persistentes, de forma que se um dos microsserviços não responda imediatamente ou esteja temporariamente offline, os pedidos sejam armazenados para serem processados quando possível. As filas seguem o modelo de um produtor e múltiplos consumidores, pois as requisições disparam tanto solicitações de consulta de estoque e de registro de transações, que são separados em bancos diferentes para que a carga entre eles possa ser distribuída de forma mais eficiente (E para que consultas pesadas de relatórios financeiros não gere atrasos de leitura para operações de estoque).<p>
As requisições vindas do módulo financeiro seguem um padrão síncrono REST, pois espero que o volume seja menor se comparado ao fluxo de clientes, e a espera do retorno de requisições não seja um fator de impedimento, diferentemente da área que interage com o cliente, que requer agilidade para processar os pedidos e gerar uma experiência de usuário fluida.<p>
Além do registro de movimento de estoque, o serviço de logging também pode disponibilizar métricas coletadas dos pedidos para um graphana para facilitar observabilidade de possíveis gargalos na infraestrutura, com as mensagens coletadas das filas tendo o tempo de entrada de um pedido e da geração de uma resposta.
Finalmente, para otimizar tanto a consulta de estoque de itens frequentemente visualizados, e para reduzir o tempo de execução de relatórios frequentes, incluiria um cache Redis nas interfaces de ambos os bancos, considerando a quantidade de requisições.

## Questão 2
Para um aplicação deste porte seguiria uma filosofia baseada no SOLID, priorizando separação entre lógica de negócio e implementação. Em `schemas` incluiria a descrição de schemas json,xml, ou de quaisquer formatos usados no sistema, para ter a estrutura esperada de objetos descrita de forma acessível para o desenvolvedor e a aplicação. De forma semelhante, em `models` incluiria a estrutura de classes usadas dentro da aplicação, seguindo de forma próxima a estrutura de diretórios dos submódulos do projeto.<p> A implementação dos componentes centrais do API incluiria em `core`, dado que são as implementações das regras de negócio do projeto. E em `repositories` incluira as interfaces de persistência de dados que definem as interações com bancos de dados.<p>Para abstrair a interface de rede, as chamadas de protocolos de redes ficariam em `routers`, e chamadas de api externas, ou de serviços internos auxiliares, ficariam em `services` e usariam da abstração dos routers.<p>
Dentro de `tests` replicaria a estrutura do projeto para os testes unitários em `unit-tests`, e testes de integração (`integration-tests`) ou end-to-end (`end-to-end-tests`) reaproveitariam mocks de módulos individuais.<p>
Incluiria também um diretório `docs` para disponibilizar a documentação, caso ela fosse escrita manualmente no mesmo repositório. Desta forma a implementação de features ou correção de issues pode ser feita com base em documentação existente em um local de fácil acesso, e a escrita de documentação seria um requisito para completar uma implementação nova.<p>

## Questão 3
`threading` é usada para instanciar threads do SO para execução de tarefas concorrentes, mas especificamente no python elas não são capazes de ser totalmente paralelas pois cada processo python consome o Global Interpreter Lock (GIL) para ter segurança na coleção de lixo do interpretador, com exceção de versões experimentais da linguagem que o desabilitam. Mas, como não geram uma troca de contexto muito pesada, podem ser adequadas para tarefas que ocupam maior parte do tempo de execução com espera por outros recursos, como abertura de arquivos ou esperas de APIs com tempo de resposta longos.<p>
`multiprocessing` cria novos processos no SO, e portanto não possui a mesma limitação de paralelismo de threads, pois cada processo instancia seu GIL. Porém, a instanciação e destruição de processos gera overhead alto, e isto pode causar perda de performance em casos onde não se tem uma quantidade alta de núcleos de CPU. Dito isto, é uma boa opção para tarefas que ficam ativas por longo tempo de processamento de operações CPU-bound, como processamento ou geração de arquivos pesados. Por exemplo, no contexto de uma aplicação ERP, a criação de relatórios financeiros com base numa quantidade grande de dados pode ser um caso de uso apropriado para multiprocessing.<p>
`asyncio` se difere de threading e multiprocessing pois habilita execução assíncrona de maior performance e maior controle, mas por consequência gera complexidade maior do design do projeto. É ideal onde se espera maior performance, e permite uso de signals do SO para orquestração mais controlada, e quando implementada adequadamente pode ser mais performática que as outras bibliotecas. No contexto de uma aplicação ERP, encaixariam bem para gerenciar as tarefas advindas das filas de mensagens descritas na **Questão 1**, podendo tirar proveito de sinais assíncronos vindo de leitura da fila para disparar a execução de novas tarefas de forma eficiente.<p>
